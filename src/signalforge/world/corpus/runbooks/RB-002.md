The orders service is thin: it validates, writes to orders-db and publishes `order.placed`. Most 5xx bursts come from the database connection pool or from the event bus.

## Symptoms
- `orders-5xx-rate` alert; HTTP 503 from `/v1/orders`.
- Logs containing `timeout acquiring connection from pool`.

## Diagnosis
1. Compare `db_pool_active` with `db_pool_max` on orders. If active equals max, the pool is exhausted; continue with RB-005.
2. Check `connections_by_client` on orders-db for every client. An unexpected client (reporting, ad-hoc analysis) holding primary connections starves orders.
3. Check event-bus health if the logs mention publish timeouts instead.
4. Review orders deployments only after the pool and event bus are ruled out; a deployment that has been stable for hours before onset is unlikely to be the trigger.

## Remediation
- Pool starvation by another client: move that client back to the replica or revoke its primary access.
- Genuine orders regression: roll back the last orders release.
