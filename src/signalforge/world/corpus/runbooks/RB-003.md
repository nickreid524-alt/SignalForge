Catalog runs on the JVM with a 4 GiB container limit. A sawtooth in `memory_usage` that ends in a restart means the heap is growing without bound between restarts.

## Symptoms
- `catalog-pod-restarts` alert; logs containing `OOMKilled`.
- `memory_usage` climbs steadily then drops to baseline on each restart.
- Long GC pauses in the logs before each kill.

## Diagnosis
1. Measure the period of the sawtooth. A stable period points at a leak proportional to traffic; a shrinking period points at a leak proportional to time.
2. Widen the deployment window: leaks often ship a day or more before the first restart. Look at the change notes of every catalog release in the last seven days for caches, buffers or new client libraries.
3. Check `request_rate`. A traffic increase raises memory level but does not by itself create a sawtooth.
4. Check `cache.max_entries` and similar configuration; a zero value usually means unbounded.

## Remediation
- Roll back to the release before the leak or set a bounded cache size and redeploy.
- Do not simply raise the memory limit; it only lengthens the period.
