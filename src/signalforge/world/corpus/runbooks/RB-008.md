The event bus is a partitioned log. Consumer lag is the number of messages (or seconds) between the newest message and the consumer's committed offset.

## Reading the signals
- `queue_lag` rising with `redelivery_count` flat: consumers are slow or too few.
- `redelivery_count` rising with consumer restarts: a message cannot be processed and is being redelivered after each crash (a poison message).
- Brief `error_rate` spikes with a leader-election alert: the controller changed leader; consumers reconnect automatically within seconds.

## Diagnosis
1. Query `redelivery_count` on event-bus and `restart_count` on the consumer.
2. If both are up, read the consumer's ERROR logs for the failing message shape and compare with the producer's recent deployments and change notes.
3. If only lag is up, check the consumer's `replica_count` and autoscaler configuration.

## Remediation
- Poison message: fix the consumer's parser or roll back the producer's schema change; the backlog drains once processing succeeds.
- Under-scaled: raise `min_replicas`.
